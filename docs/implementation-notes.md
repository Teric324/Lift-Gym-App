# Implementation notes

Decisions and reminders that do not belong in the product spec. Keep it short.

## Data model (src/db)

- Tables: `exercises`, `workouts`, `sessions`, `sets`, `drafts`, `meta`.
- `sets` holds **checked sets only**. Each has `createdAt`; editing a set keeps it, so "the oldest
  set stays the record" still holds after an edit.
- PR is never stored. It is computed from `sets` (`domain/pr.ts`), so edits and deletes are
  always reflected.
- Ids are string UUIDs from `newId()` (`crypto.randomUUID()`, with a `getRandomValues()` fallback
  because `randomUUID` is missing on plain `http://192.168.x.x`).
- Session `date` is the **local** calendar day (`localDateString`), never `toISOString()`.
- Starter exercises use fixed ids (`seed:bench-press`, ...) so two machines that each seed their
  own database still agree on ids when a JSON backup is imported. Seeding runs once, tracked by
  the `exercisesSeeded` flag in `meta`.
- Archiving an exercise is a flag. Its sets, history and PR are untouched.

## Active session and draft

- At most one session is active (`finishedAt === null`). `startSession` throws
  `ActiveSessionExistsError` if there is one.
- The draft (`drafts`) stores the active session's exercise order and which exercises were
  added, replaced or skipped. It is created with the session, deleted when it is finished or
  deleted. It does not hold unchecked set values.

### TODO for the session screen (step 9): stale active session

`prefill` ignores unfinished sessions. If the user opens the app and an active session from an
**earlier day** still exists (forgot to tap finish), starting a new session would be blocked and
prefill would not see those sets.

The UI must handle it explicitly when starting a session:

1. Detect it: `getActiveSession()` returns a session whose `date` is before today's local date.
2. Ask the user whether to finish it. Finishing keeps its checked sets and makes them count for
   history, PR and prefill.
3. Only then start the new session. Never finish or delete the old one silently.

Related: an active session with no checked sets can be offered as "discard" instead of "finish".

## Backup (src/db/backup.ts, src/features/settings)

- File: `{ app: "lift", formatVersion: 1, exportedAt, data: { exercises, workouts, sessions, sets } }`.
  Drafts are not exported. Name: `lift-backup-YYYY-MM-DD.json` (local date).
- Import replaces everything in one transaction, after strict validation (shape, value limits,
  unique ids, references) and an explicit confirmation showing counts. Unknown `formatVersion`
  is rejected. It sets the `exercisesSeeded` flag so the starter list never reloads.
- An active session in a backup gets a draft rebuilt from its checked sets (unchecked plan rows
  were never exported).
- If the phone already has data, the current data is exported first; the import does not run
  unless that export succeeded.
- Export uses `navigator.share` with the file (Share sheet: Files / iCloud Drive) when available,
  otherwise a download link. The file is prepared before the tap because iOS needs `share()` to
  start directly from the gesture.
- The reminder shows after 30 days without an export (counted from the oldest data if never
  exported). `lastExportAt` is stored in `meta`.
- Changing the format later: bump `formatVersion`, keep a reader for the old one.

## PWA (vite.config.ts, src/features/pwa, src/app)

- `vite-plugin-pwa` in `registerType: 'prompt'`, `generateSW`. A new service worker installs and
  **waits**; `skipWaiting()` runs only when the page sends `SKIP_WAITING` (the "Update available"
  button). There is no `clientsClaim`. So an update applies on the next full start of the app, or
  on tap, never by itself.
- The button is hidden while a session is active (`useActiveSession`); a note says the update is
  ready and will install later.
- The page looks for a new version when it returns to the foreground and hourly.
- Offline: everything is precached; navigations fall back to `/index.html`.
- `requestPersistentStorage()` runs at startup and stores the result in `meta` (`storagePersist`);
  Settings shows it. It never throws and does not re-ask once granted.
- iOS: `black-translucent` status bar + `viewport-fit=cover`; the top bar is always dark so the
  white status bar text stays readable, and body/header padding uses `env(safe-area-inset-*)`.
- Icons are generated by `node scripts/generate-icons.mjs` (no dependencies). The artwork is a
  placeholder; edit `BARBELL` in the script and rerun to change it.
- Dexie rule (also in CLAUDE.md): never edit an existing `version()` block; add a new one.

## Exercises and workouts UI (step 7)

- Routes: `/` workouts list, `/workouts/:id` editor, `/exercises`, `/exercises/:id`, `/settings`.
  Every edit is saved at once (no Save button); lists are live (`useLiveQuery`).
- Archive, never delete: exercises (`archived`) and workouts (`archived`, schema v2) are hidden,
  not removed, so `workoutId` in sessions and ids in backups always resolve.
- An archived exercise inside a routine stays there (shown greyed, with a remove button) and is
  left out of new sessions (`startSession`). Restoring it brings it back.
- Names: exercises are unique (case-insensitive, archived included; typing an archived name
  offers "Restore"). Workout names are free text and may repeat.
- Reordering uses up/down buttons (reliable on iOS); drag and drop can come in the design pass.
- Schema v2 (`LiftDB`): `version(1)` is frozen. `version(2)` has an upgrade that sets
  `archived: false` on existing workouts. A `versionchange` handler closes the connection so a
  newer schema can upgrade; the page then reloads (`db.onVersionChange`).
- Backup `formatVersion` 2 adds `archived` to workouts; format 1 files are still read.
- Styling is split on purpose, so a design pass does not touch components: tokens and page base in
  `src/app/theme.css`, the app shell in `src/app/layout.css`, components in `src/ui/ui.css`.
  Components use semantic class names and no inline styles.
- Settings shows the build (`<git hash> · <UTC time>`, from `vite.config.ts`) to tell installed
  copies apart.

## Workout session (step 8)

- Flow: Home `Start` -> `startSession` (draft = routine's exercises, plan rows copied from each
  exercise's last finished session) -> `/session` -> check rows -> `Finish workout`.
- One active session. Starting while one is open opens a dialog (`ActiveSessionDialog`): resume
  it; if it is from an earlier day also "finish it and start the new one" (ends it at its last
  checked set, `finishSessionAtLastSet`); "discard it" only when it has no checked sets.
  Nothing is finished or deleted without a tap.
- Everything on the session screen is read from IndexedDB (`useSessionView`, a live query) and
  every change is written at once. Closing the app loses nothing but scroll position and focus.
- `WeightField` / `RepsField` save on every valid keystroke (`readWeightText` / `readRepsText`
  in `src/domain/field-input.ts`). Empty or invalid text is never saved; an invalid text stays
  visible and marked, with a note of the value that is kept. Over 500 kg shows a note, no block.
- `WeightField`'s props (`valueGrams`, `stepGrams`, `lastGrams`, `onChange`) are the contract for
  the weight picker of the next step; `SetRow` does not need to change when the picker replaces
  the text field. `stepGrams` and `lastGrams` are passed already but not used yet.
- A checked row's stored set takes the row's position as `order`, so later pre-filling lists the
  sets in the planned order even if they were checked out of order.
- Finish asks only when unchecked rows remain (they are dropped with the draft). With no checked
  set the only exit is Discard, so empty sessions never reach the history.
- Component tests run in jsdom (`// @vitest-environment jsdom` at the top of the file) with
  Testing Library; `src/test/jsdom-dialog.ts` stands in for the missing `<dialog>.showModal`.
  The dialogs are always in the DOM, so tests wait for `dialog[open]`, not for their text.
- Session styles live in `src/features/session/session.css` and use the shared tokens.

## Weight picker (step 9)

- The row shows the weight as a button (`.weight-button`, 52 px tall, like the check button);
  a tap opens `WeightPicker`, a modal `<dialog>` mounted only while open so each opening starts
  fresh. `WeightField`'s props are unchanged, so `SetRow.tsx` did not change.
- Maths is in `src/domain/weight-picker.ts` (integers only): `nearestStep`, `pickerStart` (value,
  else last weight, else first step), `pickerWindow` (30 steps each side, from one step up to
  500 kg), `jumpCenter`. The list is built by multiplication, like `stepList`.
- Jump buttons (-25, -10, +10, +25 kg) move the window only; a tap on a value applies it and
  closes the picker. 0 kg is a separate button because the list starts at one step.
- Typing in the picker saves every valid value (same rule as before: empty and invalid are never
  saved, the last valid value stays, over 500 kg shows a note). The field is not focused on open,
  so the keyboard does not hide the list.
- iOS keyboard: the dialog is sized from `window.visualViewport` (`--vv-height`, `--vv-top`, set
  by `WeightPicker`), not from `dvh`, because on iPhone the keyboard shrinks the visual viewport
  only. The dialog stays inside it, below the status bar (`env(safe-area-inset-top)`), with the
  title, typing field and Done at the top and the list taking the remaining space.
- Tests: pure maths (`weight-picker.test.ts`), the component (`weight-field.test.tsx`, including
  a fake `visualViewport` that shrinks), and the real-database `SetRow` tests. CSS cannot be
  checked in jsdom; the geometry was checked in a real browser at 375x812 and 375x430.

## Freedom in the session (step 10)

- No schema change: `DraftItem` already had `skipped`, `origin` and `replacesExerciseId`.
- Everything is "today only" except replacing with **Update the workout**. All operations are one
  transaction each (`drafts.ts`), so an app closed in the middle leaves the old or the new state.
- **Add** (`addExerciseToDraft`): appended, rows from the exercise's own last finished session;
  archived exercises and exercises already in the session (skipped included) are refused.
- **Move** (`moveDraftItem` / `moveVisible`): swaps with the next visible exercise; skipped ones keep
  their slots and come back where they were.
- **Skip** (`skipDraftItem`): the item stays in the draft with `skipped = true` and its rows. If some
  rows are checked it needs `removeCheckedSets: true` (the UI asks first): the stored sets are
  deleted and the rows come back unchecked on **Bring back** (`unskipDraftItem`). Skipped exercises do
  not count in the finish summary.
- **Replace** (`replaceDraftExercise`, `applyReplacement`):
  - nothing checked: the new exercise takes the old one's place; the old one and its unchecked
    values are dropped;
  - some checked: the old exercise stays with only its checked rows and the new one is inserted
    right after it. Checked sets always stay on the exercise that was performed, so history and
    PR are not touched;
  - the new exercise's rows come from its own history, never from the replaced exercise's values;
  - `replacesExerciseId` points at the **routine** exercise being stood in for, also through a
    chain of replacements (`routineTargetOf`);
  - "Update the workout" swaps that routine exercise in place. It is refused (and nothing changes)
    for an item added today, when the routine no longer has the exercise, or when the new exercise
    is already in the routine. The UI disables the option with the reason.
- UI: `ExerciseMenu` (⋯), `ReplaceExerciseFlow` (single-choice `ExercisePicker`, then a dialog with
  "Only today" / "Update the workout"), `AddExerciseButton`, "Skipped" section on `SessionScreen`.
- Tests: pure helpers (`session-items.test.ts`), repo and edge cases (`session-edit.test.ts`), and
  screen flows with the real database (`session-edit-ui.test.tsx`).
